# AGENTS.md

Guide for coding agents (Claude Code and others) working on `soundstage`, the offline spatial
sound engine for Blender animations. Read [README.md](README.md) first, then the documents it
links. If `AGENTS.local.md` exists next to this file (gitignored), read it too: it holds
machine-specific paths, tools and the user's surrounding Blender workflow.

## What this repo is

- A Python package `soundstage` with two halves that never import each other's dependencies:
  - `soundstage/blender/`: runs **inside Blender's Python** (`bpy` plus Blender's bundled numpy
    only). `tag.py` is imported by scene generator scripts; `bake.py` is run headless to export a
    scene file.
  - `soundstage/engine/` and `soundstage/cli.py`: run in the **repo venv**
    (numpy, scipy, soundfile, soxr, numba, pyloudnorm). No `bpy`.
- `soundstage/__init__.py` must stay free of third-party imports, so that Blender can import
  `soundstage.blender` without the engine's dependencies.
- The contract between the halves is the scene file ([docs/spec/scene-format.md](docs/spec/scene-format.md)).
  Change it only together with its `version` field and the spec.

## Environment

- Linux, Python 3.12+. Always use the repo venv (`python3 -m venv .venv && .venv/bin/pip install
  -e '.[dev]'`); do not rely on system packages.
- Blender 5.x on `PATH` (`blender -b`), headless is enough: bake needs no GPU, display or audio
  device. Always `blender -b <file> --factory-startup -y --python ...`.
- `ffmpeg` / `ffprobe` on `PATH` for previews and for inspecting files.
- Headless machines without a GPU often have no EGL: Workbench and EEVEE cannot render there
  (`libEGL.so.1` missing). Tests that need frames render them with Cycles on the CPU at 64×36,
  1 sample (about 30 ms per frame).
- Scene files store absolute sample paths; bake and render on machines that see the same paths.
- Machine-specific details (paths, hosts, surrounding tools) belong in `AGENTS.local.md`, never in
  tracked files.

## Commands (see [docs/spec/cli.md](docs/spec/cli.md))

```bash
.venv/bin/pytest                                   # all tests; Blender tests skip without blender on PATH
.venv/bin/pytest -m "not blender"                  # unit tests only (fast)
.venv/bin/python tools/make_test_samples.py        # generate samples/*.wav
.venv/bin/soundstage scan <blend> --out scan.json  # cameras and sound-source candidates
.venv/bin/soundstage bake <blend> --run sounds.py --out <dir>   # headless Blender → scene.json + scene.npz
.venv/bin/soundstage inspect <dir>/scene.json      # table of sources and distances
.venv/bin/soundstage render <dir>/scene.json -o <mix.wav> --report --plot
.venv/bin/soundstage presets [TEXT]                # reverb environments for --set reverb=<name>
.venv/bin/soundstage preview <mix.wav> --frames <frames dir>   # MP4 for a sync check (ffmpeg)
```

Asked to add sound to an animation? Follow [docs/agent-guide.md](docs/agent-guide.md). Writing scripts
that build scenes? [docs/scene-builder-guide.md](docs/scene-builder-guide.md).

## You cannot listen: verify with numbers and pictures

An agent has no speakers. Every claim about how a render sounds must rest on something measurable:

- the render report (`<mix>.report.json`): peaks, true peak, LUFS, loudness range, per-source
  distance, delay and playback-rate ranges, visibility, audible frames, warnings;
- the debug plot (`<mix>.plot.png`): per-source distance, level, pan, delay, pitch and visibility
  over time, on a frame axis; read it as an image;
- known-answer tests: put a synthetic source where the answer is known (distance, side, speed)
  and assert the measured level, channel balance, onset time or frequency;
- spectrograms of the output (`scipy.signal.spectrogram` → PNG) for filters and Doppler sweeps.

Say plainly what was measured and what still needs the user's ears. The user's listening
judgement in Resolve is the final check; ask for it at phase ends.

## Conventions

- Code reads like the surrounding code: module docstrings state the responsibility, type hints on
  public functions, dataclasses for structured data, no classes where a function will do.
- DSP is vectorized numpy per chunk; per-sample recursions (time-varying filters, delay reads) go
  in small `numba.njit` kernels with a plain-numpy reference implementation used by the tests.
- All randomness (loop phases, variations) is seeded from the source id, so renders are
  bit-for-bit reproducible (NFR-2).
- Units: metres, seconds, Hz, dB in parameters; linear gain and samples internally. Names carry
  the unit when ambiguous (`gain_db`, `cutoff_hz`, `delay_s`, `delay_samples`).
- Defaults live in one place (`soundstage/blender/schema.py`) and are documented in
  [docs/spec/signal-model.md](docs/spec/signal-model.md) and [docs/spec/tagging.md](docs/spec/tagging.md);
  keep the three in sync.

## Learning loop

Write down what was learned in the same round of work:

- a model's formulas, choices, alternatives and limits on its page in `research/models/`; a
  measurement behind a choice as an experiment in `research/experiments/` with a script that
  reproduces every number; sources in `research/papers/README.md` (and `fetch.py` if openly
  available);
- the resulting formulas and starting values in `docs/spec/signal-model.md`; hard-to-reverse
  decisions as an ADR;
- Blender-side lessons (bake, depsgraph, custom properties, headless audio) in `docs/` or
  `research/`, so that agents building scenes elsewhere can reuse them.

## Git

- Commit only when the user asks. Commit messages are technical and direct: what changed and why.
- No AI attribution anywhere (no `Co-Authored-By`, no "Generated with" lines) in commits, PRs,
  issues, code or docs.
- Binaries (WAV, NPZ, MP4, .blend) stay out of git; they are rebuilt from scripts.
